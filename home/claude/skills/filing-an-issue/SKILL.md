When the user asks you to make an issue about something, the user doesn't want
to deal with it now. Don't discuss it, don't start work on it, and don't ask the
user what the user wants in it. Capture what you know from the conversation and
the code, and file it.

## Where

File it in the issue tracker that the user names. Otherwise use the tracker that
the project's instructions or memories say it uses, which may be Linear, with
the team that they name. If nothing names one, use the GitHub repository of the
project that you are working in, which you can find from the repository's
remote.

## What to write

Write it so that someone who wasn't in the session could act on it. The title
names the problem or the request. The body says:

- what is wrong or wanted, and where, with links to the files, lines, pull
  requests and issues involved;
- what you saw and how to reproduce it, if it is a problem;
- what you know about the cause, and what you have ruled out;
- what you don't know.

Write what you don't know in the issue. Don't ask the user about it. Write only
what you observed or read. Quote real output, and say "not measured" when you
measured nothing.

Put in the issue only what someone acting on it needs. Leave out anything about
the user or the user's other projects that they don't need.

## When to ask

Ask the user only if someone couldn't act on the issue without the answer, for
example because you can't tell what the problem is, or which repository or
Linear team it belongs to. Ask everything that you need in one message, then
file the issue.

## After filing

Reply with the link to the issue, or its identifier, and nothing more. Filing
it, including the choice of tracker or team, needs no callout and no agenda
item. Then go back to what you were doing.
